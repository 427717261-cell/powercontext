# 量化 × 后端 实测结果

一次进程内跑完四档，同一浏览器实例、同一网络环境、同一 Node 后端，横向可比。
每项取 3 轮中位数，文档向量化的首轮（含算子/shader 预热）已剔除。

- 机器：Windows 11 / Core Ultra 5 125H / 16 GB，`hardwareConcurrency=18`
- 浏览器：Edge 156（Chromium 156），`--enable-unsafe-webgpu` 启动
- 模型：`Xenova/bge-small-zh-v1.5`（512 维），ONNX 由浏览器本地加载，无外部 embedding 服务
- seekdb：`122.51.213.86:2881` / `stepfun_kb`，健康检查 18.1 ms
- 语料 30 篇 / 查询 12 条 / 批大小 8
- `crossOriginIsolated=True`（决定 WASM 能否多线程）

## 汇总

|---|---|---|---|---|---|---|---|---|---|---|---|
| FP32 · WASM（量化前基线） | WASM | 90.46 MiB | 1.00× | 5.65 s | 19.7 篇/s | 25.4 ms | 161.6 ms | 252.2 ms | 1.00 / 1.00 | 0.9898 | 基准 |
| INT8 · WASM | WASM | 22.90 MiB | 3.95× | 527 ms | 39.7 篇/s | 13.7 ms | 163.7 ms | 230.5 ms | 1.00 / 1.00 | 0.9898 | 0.98811 |
| FP32 · WebGPU | WEBGPU | 90.46 MiB | 1.00× | 1.01 s | 71.9 篇/s | 18.6 ms | 132.7 ms | 206.0 ms | 1.00 / 1.00 | 0.9898 | 1.00000 |
| FP16 · WebGPU | WEBGPU | 45.30 MiB | 2.00× | 1.10 s | 68.3 篇/s | 51.6 ms | 93.3 ms | 218.4 ms | 1.00 / 1.00 | 0.9898 | 0.99998 |

## 怎么读这张表

1. **体积与质量**：INT8 把 90.46 MiB 压到 22.9 MiB（3.95×），FP16 压到 45.3 MiB（2.00×），
   而混合检索 Recall@10 全部保持 1.00、nDCG@10 全部 0.9898，没有可观测的质量损失。
   向量余弦 0.98811（INT8）与 0.99998（FP16）说明向量本身只是轻微扰动，排序结果未变。
2. **后端差异**：FP32 下 WebGPU 向量化 71.9 篇/s vs WASM 19.7 篇/s，约 3.6 倍。
   这个差距在批大小 8、文本只有十几字的条件下取得，原因是 WASM 后端受 SIMD 与线程调度限制。
3. **检索延迟**：seekdb 侧 93–164 ms，波动主要来自公网往返（云服务器）而非数据库内核，
   同一轮内 FP16·WebGPU 的 93.3 ms 明显低于其他三档，属于网络抖动，不宜解读为后端差异。
4. **端到端**：206–252 ms，其中向量化占比很小，瓶颈在网络往返。
5. **一个反常点要说清**：FP16·WebGPU 的单条查询向量化 51.6 ms 反而高于 FP32·WebGPU 的 18.6 ms。
   单条查询 batch=1，GPU 占用率极低，FP16 的权重转换与调度开销无法被摊薄，
   属于小 batch 下的已知现象。它并不影响文档批量向量化（68.3 篇/s 与 FP32 基本持平），
   实际使用中查询侧建议保持 FP32，批量导入再启用 FP16。

## 复现方式

```bash
node scripts/run-bench-headless.mjs \
  --configs fp32-wasm,q8-wasm,fp16-webgpu,fp32-webgpu \
  --rounds 3 --batch 8 --out bench/results-final.json --webgpu
```

原始数据见 `results-final.json`（含每条查询的命中与指标，可自行复算）。

## 已经排除的错误结论

早期用"分进程各跑一半 + 向量化只计单次"的方式测过一轮，得出过
"WebGPU 向量化比 WASM 慢 3 倍"的结论。那是测量方法造成的假象：跨进程不可比，
且首轮预热被计入。作废数据保留在 `archive-v1/`，不参与任何对外结论。
