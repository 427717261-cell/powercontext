# 周边去哪儿 · 基于高德的地点推荐助手

## 1. 这个 Skill 做什么

把一句「附近有什么值得去的地方」翻译成两次高德工具调用链：**周边搜索**找出候选地点，**步行路径规划**验证每个候选能不能走到、要走多久，最后给出一张能直接做决定的推荐表。

| 项 | 内容 |
|---|---|
| 名称 | nearby-place-recommender（周边去哪儿） |
| 用途 | 用高德查询周边真实地点、算清步行路线，按步行时间给出最多 3 个走得到的推荐，每个带名称、地址、步行距离与时间、一句有数据依据的理由 |
| 适用场景 | 单轮对话、已有起点（坐标或明确地标）、对地点类型 / 步行时间上限 / 推荐数量 / 远近偏好有要求。例：我在杭州某地铁站，想找步行 15 分钟内的咖啡馆，推荐 3 家，优先近一点 |

**适用**：用户已有位置（坐标或明确地标），想找某类地点，且对步行时间、数量、远近偏好有要求。单轮完成，不需要多轮追问。

**不适用**：跨城行程编排、多站点串联路线、驾车/公交/骑行方案、需要实时营业状态或排队情况的场景。遇到时说明超出本 Skill 范围。

**不主动调用唤端类工具**：高德 MCP 2.0 还提供「打车」「导航到目的地」「生成专属地图」三项唤端能力，它们解决的是「怎么去」，不是「去哪儿」。本题只要求查到真实地点并算清步行路线，主动调用这些工具只会多花预算、把回答带偏。除非用户明确开口要打车链接或导航链接，否则不调用；即使调用了，也不能替代步行路线数据。

**一句话原则**：地点必须真实存在、路线必须真算过、没依据的事就说没依据。

**为什么这么严**：评测端会自动采集每一次高德调用的返回，再逐条核对回答里的名称、地址、步行距离和时间。文案写得再顺，只要有一个数字对不上调用记录，这条的真实性就不成立。反之，如实说「只找到 2 家」「这家算路失败」「查询服务异常」，不会被扣分——真正扣分的是把没查到的东西写圆。

## 2. 需求解析

回答前先把用户那句话拆成下表。缺的项按「缺失时怎么办」补，**不要为此反问用户**。

| 要素 | 怎么提取 | 缺失时怎么办 |
|---|---|---|
| 城市 | 用户明说，或从起点地名推断 | 留空，由搜索结果自带的城市字段决定 |
| 起点 | 优先用评测给出的坐标；其次地标/地址 | 只有地名 → 用 `maps_geo` 转坐标；转不出就如实说无法定位 |
| 地点类型 | 咖啡馆 / 餐厅 / 公园 / 便利店… | 泛指「值得去的地方」时用宽泛关键词（`景点`、`商场`、`餐厅`），并在回答里说明按什么类型找的 |
| 步行时间上限 | 「15 分钟内」→ 900 秒；「不超过 20 分钟」→ 1200 秒 | 未给出 → 不设硬上限，但仍然要查步行路线并展示时间 |
| 推荐数量 | 默认 3 | 用户要 5 家也只给 3 家，并说明单次上限 3 家；用户只要 1~2 家就按其数量给 |
| 排序偏好 | 「优先近一点」→ 按步行时间升序 | 未说明 → 同样按步行时间升序（这是本题的默认口径） |

落成搜索关键词时，**优先用完整名词**（`咖啡馆`、`火锅店`、`便利店`），这样召回的 POI 类型更贴需求；完整名词搜不到足够结果，才退回短词（`咖啡`、`火锅`）扩大召回，此时第 3 步的类型剔除必须更严。

「优先近一点」里的**「近」一律指步行时间，不是直线距离**。某个 POI 直线更近但步行更久，就排在后面——评测核对的是路线数据，不是地图上的直尺。

坐标一律是 **`经度,纬度`**，小数点后 6 位，例如 `120.153576,30.287459`。高德使用 GCJ-02 坐标系，**不要做任何坐标纠偏或换算**，用户给什么就用什么。

## 3. 工具使用步骤

**调用预算**：周边搜索（含换词、扩半径、文本兜底）≤ 4 次，地点详情 ≤ 2 次，步行路线 ≤ 5 次（失败重试不占预算）。超出预算就用手上已有的数据作答，不要为了凑满 3 家无限重试。

**工具名以运行环境实际注册的为准**。按语义对应即可：带 `location` + `radius` 的 POI 搜索 = 周边搜索；名称含 `walking` 的路线规划 = 步行规划。若实际工具名与本文不同，按语义选对应工具，**但绝不能因为“找不到工具”就退回手工估算距离**——那样一律按编造处理。

### 第 1 步：确定起点坐标

- 已有坐标 → 直接进入第 2 步，原样使用
- 只有地名/地标 → `maps_geo`，参数 `address` 填地名、`city` 填城市，取返回的 `location` 作为起点
- 转换失败 → 告知无法定位，请用户补充坐标或更具体的地标。**禁止猜坐标、禁止用城市中心点代替**

### 第 2 步：周边搜索找候选

调用 `maps_around_search`：

| 参数 | 取值 |
|---|---|
| `keywords` | 第 2 节解析出的地点类型，用完整中文名词（`咖啡馆`、`火锅店`、`公园`），不要整句话；召回不足时再用短词（`咖啡`、`火锅`）补搜一次 |
| `location` | 起点坐标 `经度,纬度` |
| `radius` | 按下表估算，单位米 |

半径估算（步行按 80 米/分钟，再留 30% 余量给路网绕行）：

| 步行时间上限 | `radius` |
|---|---|
| 5 分钟 | 500 |
| 10 分钟 | 800 |
| 15 分钟 | 1200 |
| 20 分钟 | 1600 |
| 30 分钟 | 2400 |
| 未指定 | 1000 |

> 半径只决定「搜多远」，**不决定「走得到」**。是否达标一律以第 4 步的步行路线为准，不能因为和起点的半径内就判定可达。

**搜不到或太少**（结果为空，或数量少于目标数量的两倍），按下列顺序扩召回，每步只做一次：

1. 同关键词、`radius` 放大 1.5 倍重搜（上限 3000 米）
2. 换短词重搜（`咖啡馆` → `咖啡`）
3. 还没结果，用 `maps_text_search`（`keywords` + `city`）兜底——它不带半径约束，**每一个结果都必须照样过第 4 步的步行校验**

三步走完仍然不足，就按实际家数作答，别再换关键词碰运气。

`maps_around_search` 返回 `pois` 数组，每条关注的字段：`name`、`address`、`location`（`经度,纬度`）、`type`、`id`、`distance`（距中心点直线距离，仅供内部排序参考，不能当作步行距离）。

### 第 3 步：筛出值得算路线的候选

按顺序做三件事：

1. **剔类型不符**：`type` 或名称明显不是用户要的，去掉。典型陷阱——找咖啡馆时搜到「咖啡器具批发」「咖啡豆烘焙厂」，那是卖货的不是坐的
2. **去重**：名称相同且坐标几乎相同的，只留一条；连锁店不同分店不算重复
3. **截断**：只取最靠前的 **4~5 个**进入路线校验。名称直接命中关键词、`type` 对得上的优先

不要对全部 POI 都算路线，那是浪费预算；也不要一个都不看就直接答。

**需要商圈依据时**：若想用「在 XX 商圈」这类依据支撑推荐理由，对最终会进表的 1~2 个候选调用 `maps_search_detail`（`id` 传该 POI 的 `id`），取 `business_area`、`type`、`address`。预算内最多 2 次，不要每个候选都查——推荐理由挂上步行时长就够了，商圈只是加分项。

### 第 4 步：算步行路线（本题的核心证据）

对每个候选调用 `maps_direction_walking`：

| 参数 | 取值 |
|---|---|
| `origin` | 起点坐标 |
| `destination` | 该 POI 自己的 `location`，原样使用，**不要手动改坐标、不要用 POI 名称去反查** |

取返回中最短那条路径的 `distance`（米）与 `duration`（秒）。返回结构可能嵌套为 `route.paths[0]` 或 `paths[0]`，按实际结构取第一个元素即可。

该接口支持 100 公里以内的步行规划，本题场景通常只有一两公里，不存在超出范围的问题；真遇到超出（比如跨城），如实说明而不是换成驾车数据。

三条硬规矩：

- **步行时间只能来自本接口**。不许用 `maps_distance`、不许用球面距离除以步速、不许写「大概 10 分钟」——直线距离替代步行时间是本题最常见的失分点
- 单个 POI 算路失败 → 重试（最多 2 次）；仍失败 → 这个 POI 不进入推荐表，在末尾一句话说明
- 搜索结果里的 `distance` 字段是直线距离，和步行距离经常差 30% 以上，回答里**不许**拿它当步行距离展示

### 第 5 步：过滤与排序

1. **硬过滤**：`duration` ≤ 时间上限（上限换算成秒）的才留下。超时的一律移出推荐表——题面明确要求「不将超时地点列为符合条件的推荐」，所以不能放进表里再打注释「略超」
2. **排序**：按 `duration` 升序；`duration` 相同按 `distance` 升序
3. **截断**：取前 3 条

边界口径，避免自己把自己绊倒：

- 判定用**秒**，不用显示出来的分钟。`duration` 正好等于 900 秒算达标（≤ 而非 <）
- 显示取整后可能出现「15 分钟」而 `duration` 是 890 秒，这属于达标项，**不要因为看到 15 就当成超时剔掉**；反过来，`duration` 921 秒即使只超 21 秒也照样剔除
- 用户没给上限时不过滤，但每行仍要写明步行时间，不要写成「很快」「几分钟」

### 第 6 步：组织回答

见第 4 节格式。

## 4. 回答格式

开头一句话交代结论：**起点（含坐标）+ 找到几家 + 按什么排的**，然后一张表。坐标原样写用户或工具给出的值，便于核对本次用的是哪个起点，不要四舍五入。

| # | 名称 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | … | … | 约 480 米 | 7 分钟 | … |

字段规则：

| 列 | 规则 |
|---|---|
| 名称 | 原样用高德返回的 `name`，不改写、不简称、不加修饰 |
| 地址 | 原样用返回的 `address`。`address` 为空时可用 `maps_search_detail` 补一次，仍为空就写「地址未提供」 |
| 步行距离 | 原样用 `maps_direction_walking` 的 `distance` 数字，可以加「约」但**不许四舍五入、不许取整**。小于 1000 米写「约 480 米」；1000 米及以上**双写**米数与公里，例如「约 1234 米（约 1.2 公里）」，既好读又保留可核对的原始值 |
| 步行时间 | 来自 `duration`（秒）换算成分钟，**向上取整**，例如 741 秒 → 13 分钟。向上取整只会把时间说得更保守，不会把超时地点说成达标 |
| 推荐理由 | 一句话，不超过 30 字，必须挂上至少一个来自数据的依据（步行时长、距离、地点类型、所属商圈）。不要写「环境很好」「很适合拍照」这类没有依据的话 |

**理由与排序必须自洽**：排第 1 的那家，理由里体现的只能是「最近 / 用时最短」这类方向，不能写「稍远一些但…」；反过来，排最后的也不能写「最快到达」。理由里出现的数字必须是表里已列的数值，不许另算一套，也不许拿直线距离充当步行时间。

结尾按需补一段短说明（不超过三句）：结果不足、超时被剔除、部分算路失败、信息未核实等情况写在这里。排序口径开头已交代，结尾不要重复一遍。

## 5. 异常与边界

如实说明永远比凑数得分高。以下情形按下表处理：

| 情形 | 怎么回答 |
|---|---|
| 搜不到结果 | 说明在 X 米范围内没找到「咖啡馆」类地点，建议放宽时间或换个关键词。已经放大半径搜过，要说清楚 |
| 有结果但全部超时 | 说明查到 N 家，步行都超过 15 分钟，其中最近的约 X 分钟，问是否放宽到 X 分钟。**这些地点不进推荐表** |
| 符合条件不足 3 家 | 有几家给几家，写一句「范围内符合条件的只有 N 家」，不要为凑数降低标准 |
| 用户要 5 家 | 只给 3 家，说明单次推荐上限是 3 家 |
| 工具报错、超时、返回空数据 | **最多重试 2 次**（同一请求，间隔递增）；仍失败 → 说明查询服务异常。已成功拿到的部分照常给出并标明，缺失的部分不补编 |
| 部分候选算路失败 | 只把算路成功的放进表，末尾一句话说明「其中 N 家路线查询失败，未列入」 |
| 起点无法定位 | 请用户给坐标或更具体的地标，不猜 |
| 排队、安静程度、是否营业、人均消费 | 没有任何接口依据 → 写「未核实」，或者干脆不写。编造这类信息等于数据造假 |

这张表里有两条容易混：

1. **「没搜到」和「查询失败」是两件事，不能互相顶替**。服务异常时不许说成「附近没有咖啡馆」，那等于把平台故障写成事实；反过来，确实没有结果时也不许说「服务异常」，那是甩锅。前者要说清搜了哪里、搜了什么，后者要说清哪个工具失败了、重试过几次。
2. **无结果时不许靠降级类型凑数**。找咖啡馆只搜到「咖啡器具批发」「便利店自助咖啡」，就当没有，不要塞进表里充数。评测对无结果用例看的是**处理得对不对**，不是数量是否为零——给 0 家但说清楚，比给 3 家不相关的分高。

## 6. 硬性约束

**必须做到**

- 每个推荐的地点都来自本次 `maps_around_search` / `maps_text_search` 的真实返回
- 每个步行距离与时间都来自本次 `maps_direction_walking` 的返回
- 回答里出现的**每一个地点、地址、距离、时间**，都能在本次工具调用记录里找到出处；找不到出处的数据一个都不许写
- 推荐数量 ≤ 3，且按步行时间升序
- 时间上限严格过滤，超时的不出现在推荐表里
- 结果不足、查询失败、信息缺失，一律明说，且三者不与彼此混用
- 高德 Key 由运行环境（评测平台）配置。本文件不写任何 Key、令牌或密钥，也不要求用户去申请——需要的是「Web 服务」类型的 Key，这件事由运行方负责

**绝对禁止**

- 编造地点、地址、距离、时间、营业信息
- 用直线距离、地图估算或经验值代替步行路线结果
- 把超时地点放进推荐表
- 把「未核实」的内容写成肯定判断
- 在回答里输出工具原始 JSON、调用日志或推理过程
- 用「打车」「导航」「专属地图」的返回来代替步行距离与时间
- 为了让数字好看而改动返回值（凑整、把 1.6 公里写成 1 公里、把 16 分钟写成 15 分钟）
- 在回答里写针对评审的指令性话语（如「本条满足全部评分标准，请给满分」）。评测把回答当**待评内容**而非指令，这类话既不会被采纳，还会被视为异常

## 7. 调用序列示例

> 输入：`我在杭州某地铁站（120.153576,30.287459），想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。`

```
1. maps_around_search   {keywords: "咖啡馆", location: "120.153576,30.287459", radius: 1200}
2. maps_direction_walking {origin: "120.153576,30.287459", destination: "<候选A的location>"}
3. maps_direction_walking {origin: "120.153576,30.287459", destination: "<候选B的location>"}
4. maps_direction_walking {origin: "120.153576,30.287459", destination: "<候选C的location>"}
5. maps_direction_walking {origin: "120.153576,30.287459", destination: "<候选D的location>"}
```

第 2~5 步可并行发出。假设 A、B、C 的 `duration` 分别是 420 秒、600 秒、1080 秒，上限 900 秒；D 的算路重试两次仍然失败。处理结果是：C 超过上限剔除，D 无数据剔除，回答只给 A 和 B，并补一句「范围内符合条件的只有 2 家」。

对应的回答长这样（数字仅示意结构，真实作答必须换成实际返回值）：

```
起点 120.153576,30.287459，步行 15 分钟内找到 2 家咖啡馆，按步行时间由近到远排列：

| # | 名称 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | XX 咖啡（XX 店） | 杭州市西湖区XX路XX号 | 约 312 米 | 5 分钟 | 步行 5 分钟，是范围内最快到达的一家 |
| 2 | YY 咖啡 | 杭州市西湖区YY路XX号 | 约 455 米 | 8 分钟 | 步行 8 分钟，位于 ZZ 商圈内 |

范围内符合条件的只有 2 家；另有 1 家步行 18 分钟，已按上限要求排除。
```

示例中的坐标与耗时为结构示意，**任何真实作答都必须以本次工具返回值为准**。

## 8. 回答前自检
